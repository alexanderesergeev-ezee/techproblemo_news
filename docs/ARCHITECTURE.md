# Архитектура 0.1

Проектная схема, не схема уже развёрнутого приложения. Диаграммы записаны в Mermaid для версионирования рядом с кодом.

## Компоненты
```mermaid
flowchart LR
  SOURCES["Допущенные источники\nRSS / API / Telegram с разрешениями"] --> INPUT["Адаптер получения\nкурсор и точные повторы"]
  subgraph HOST["Существующий сервер-кандидат: Selectel Ellery"]
    subgraph APP["Один Python-сервис / один контейнер"]
      INPUT --> DB[("SQLite\nматериалы / анализы / доставки")]
      DB --> CLASSIFY["Классификатор\nтолько новые версии"]
      CLASSIFY --> VALIDATE["Проверка JSON\nscore > 0.70"]
      VALIDATE --> DB
      DB --> SEND["Отправитель\nучёт результата доставки"]
    end
    DB -. "консистентная копия" .-> BACKUP["Резервная копия\nзатем вне сервера"]
  end
  CLASSIFY --> LLM["Внешний LLM API\nодин провайдер"]
  LLM --> VALIDATE
  SEND --> TG["Telegram Bot API"]
  TG --> OWNER["Личный диалог\nпользователя с ботом"]
```

Справочник допускает несколько типов источников, но в первом live-проходе реализуется **один** тип. Telegram Bot API для доставки не означает наличие доступа к чужим каналам для чтения.

Веб-сервер, публичные входящие порты, домен, webhook, очередь сообщений как отдельный сервис и локальная LLM для этой схемы не требуются. Сеть нужна для разрешённых исходящих API-вызовов. При появлении входных updates их получение — функция того же приложения.

## Успешный проход
```mermaid
sequenceDiagram
  participant W as Worker
  participant S as Допущенный источник
  participant D as SQLite
  participant L as LLM API
  participant T as Telegram Bot API
  W->>S: Получить очередную страницу новых материалов
  S-->>W: Материалы и данные пагинации
  W->>D: Транзакция: новые записи + безопасное продвижение курсора
  W->>D: Выбрать новую версию текста
  W->>L: Текст как данные + classify_v1
  L-->>W: JSON
  W->>W: Проверить схему, цитаты, контекст и порог
  W->>D: Транзакция: анализ + PENDING delivery при прохождении
  W->>D: Зафиксировать SENDING
  W->>T: sendMessage в разрешённый личный chat_id
  T-->>W: Успех и telegram_message_id
  W->>D: Зафиксировать SENT и telegram_message_id
```

## Неопределённый исход отправки
```mermaid
sequenceDiagram
  participant W as Worker
  participant D as SQLite
  participant T as Telegram Bot API
  participant O as Оператор
  W->>D: PENDING → SENDING
  W->>T: sendMessage
  Note over W,T: Ответ потерян: сообщение могло быть доставлено
  W->>D: SENDING → UNKNOWN
  Note over W,D: Не повторять отправку автоматически
  O->>T: Проверить личный диалог обычным клиентом
  O->>D: Через служебную команду подтвердить исход или разрешить повтор
```

Равным образом обрабатывается падение процесса после успешной отправки, но до сохранения SENT. Локальная SQL-транзакция не может атомарно охватить внешний Telegram API.

## Эволюция продукта через Codex
```mermaid
sequenceDiagram
  participant U as Владелец
  participant C as Codex Web
  participant G as GitHub
  participant CI as GitHub Actions
  U->>C: Ограниченная задача и выбранная ветка
  C->>G: Читать AGENTS, SPEC, STATE и относящийся код
  C->>C: Уточнить изменение требований, внести код и тесты
  C->>G: Ветка и pull request
  G->>CI: Проверки на синтетике, без production-секретов
  CI-->>G: Результаты
  U->>G: Проверить diff и принять PR
  Note over U,G: Деплой — отдельное действие после приёмки
```

## Почему это минимально для заданной задачи
SQLite одновременно даёт постоянные данные, курсоры, историю решений и очередь отправки. Внешняя LLM снимает необходимость держать модель на 4 GB RAM. Один процесс уменьшает количество компонентов; состояние в базе позволяет пережить перезапуск. Резервирование и UNKNOWN необходимы не из-за масштаба, а из-за неизбежной возможности сбоев.

Это не доказательство глобальной оптимальности. Пересматривать при нескольких получателях с независимыми настройками, нескольких пишущих экземплярах, большом потоке медиа или требованиях высокой доступности.
