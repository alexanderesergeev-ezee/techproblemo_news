# Эксплуатация: проект runbook

Команды приложения пока не реализованы. Операции с сервером этим пакетом не выполнялись.

## 1. Сервер
Из переписки «Идеи для сада 2»: Selectel, сервер Ellery, регион ru-6a (Москва), 2 vCPU, 4 GB RAM, 60 GB SSD, Ubuntu 24.04.4 LTS. Ранее там работал другой проект; для временного MCP обсуждалось отдельное контейнерное размещение, не затрагивающее staging. Исторические настройки не подтверждают текущую загрузку или доступность.

До решения о совместном размещении выполнить только чтение:
```sh
free -h
df -h
uptime
docker stats --no-stream
```
Команды не выводят env-файлы и токены. Изучить свободную память, место и пиковую нагрузку существующего приложения. Резерв примерно 1 GB памяти и несколько GB диска — ориентир для проверки, а не гарантия достаточности. Не обновлять весь сервер и не останавливать старые проекты ради установки MVP.

## 2. Изоляция
Отдельная папка `/opt/techproblemo_news`, отдельный Compose project и отдельный локальный volume. Предлагаемый начальный предел контейнера — 0.5 CPU и 768 MB RAM; уточнить после измерения. Не переносить эти цифры в обещание фактического потребления.

Контейнер запускается не от root, без privileged, без host network и Docker socket. Нет входящих портов. Только исходящий HTTPS к выбранным API/источникам. Модель работает у провайдера, не на Ellery. Реальные секреты хранятся на сервере в закрытом `.env` с ограниченными правами, не в GitHub и не в чатах. Сертификаты проверяются; `verify=False` запрещён.

Нельзя применять глобальные `docker system prune`, `docker compose down -v` или перезапускать чужой Compose project. Имя проекта и путь указываются явно.

## 3. Бот и ключи
Владелец создаёт бота через BotFather и начинает с ним диалог. Получить свой chat_id отдельной диагностикой без вывода токена в URL/логи. Конфигурация должна проверять allowlist получателя. Username бота и chat_id не заменяют bot token.

У input-адаптера и output-бота разные полномочия. Чтение Telegram через пользовательскую сессию — отдельная, не включённая автоматически возможность. Такая сессия чувствительна как учётные данные: не передавать её coding-агенту.

## 4. Развёртывание после приёмки
TASK-004 должен создать точные команды, которые соответствуют фактическому коду. Ожидаемый процесс: выбрать принятый commit → сделать консистентную копию базы → применить проверенную миграцию → запустить только новый Compose project → сделать smoke test без массовой отправки → проверить очередь и логи.

CI запускает тесты; автоматического деплоя в первом пакете нет. Codex не получает ключ SSH сервера. При откате учитывать совместимость схемы базы; возврат старого образа не всегда отменяет миграцию.

## 5. Резервные копии
Создавать консистентную копию SQLite через Backup API/эквивалент, а не копировать вслепую один активный `.db` при WAL. Рекомендуемая начальная частота — ежедневно. Проверять `integrity_check` копии, хранить несколько поколений и сделать хотя бы одну пробу восстановления.

До постоянного запуска определить способ копирования вне Ellery: существующая система резервирования либо отдельное объектное хранилище. S3 здесь — возможное место резервной копии, не рабочая БД. Срок хранения согласовать с разрешениями на тексты.

При восстановлении сначала выключить реальные отправки. Возврат старой БД может потерять знания о уже отправленных сообщениях: не включать sender до сверки новых и восстановленных состояний. Сохранять актуальную БД, а не перетирать её единственной копией.

## 6. Диагностика
Вывести в служебной команде: время последнего успешного чтения каждого источника, новые/классифицированные/отправленные, FAILED/UNKNOWN, возраст очереди, usage и версию приложения/промпта. Логи — ротация, без токенов, полных текстов и HTTP-заголовков авторизации.

Полный отказ сервера невозможно надёжно сообщить с самого отказавшего сервера: при переходе к постоянной работе добавить внешний контроль, отдельно от MVP-логики.
